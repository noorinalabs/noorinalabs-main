The `noorinalabs-pipeline` B2 bucket is the batch graph-load transport: `scripts/publish_parquet.py` (producer, da#342/#343, in data-acquisition) uploads `data/curated/`+`data/staging/` to it; `deploy-data-load.yml` (consumer, deploy#546/#547) downloads from it onto the VPS via rclone. `make publish-parquet` (or `PARQUET_REF=<ref> uv run python scripts/publish_parquet.py`). Default ref `staged/narrator-resolve/<UTC-date>-<git-short-sha>`.

**Two keys, same env-var NAME, different value by location (owner decision 2026-07-08, "local write, GH read-only", least-privilege):**
- **GitHub Actions secret** `PIPELINE_B2_KEY_ID`/`PIPELINE_B2_KEY` = **READ-ONLY** key (caps `listFiles,listKeys,readFiles,listBuckets`). Correct for the VPS consumer — it only downloads.
- **Local `~/.zshenv`** `PIPELINE_B2_KEY_ID`/`PIPELINE_B2_KEY` = **WRITE-capable** key (needs `writeFiles`; `deleteFiles` for overwrite/cleanup), scoped to bucket `noorinalabs-pipeline`. Required for `publish_parquet.py` (producer). Owner must mint this in the B2 console (App Keys → scope to bucket) — orchestrator cannot.

**Three distinct B2 keys total** (docs/secrets-audit-2026-04-24.md): `B2_*` (backups → `isnad-graph-backups`, backup.sh), `TF_STATE_B2_*` (terraform state), `PIPELINE_B2_*` (this pipeline bucket).

**Gotchas that cost time:**
- **z4h `~/.zshenv` early-return:** the zsh4humans block runs `[[ -o no_interactive && -z "${Z4H_BOOTSTRAPPING-}" ]] && return` near the top — for a NON-interactive shell (the agent Bash tool) this returns out of `.zshenv` entirely, so any `export` placed BELOW it never reaches the tool env (works fine in the user's interactive terminal, so it *looks* set). Fix: put the exports at the very TOP of `~/.zshenv`, above the z4h block.
- **Read-only key write failure is misdiagnosed by rclone:** a write with a read-only key fails `ERROR failed to create bucket: Unknown 401 unauthorized` — this is NOT a bucket-creation-permission problem and `--b2-no-check-bucket` (`RCLONE_CONFIG_PIPELINE_NO_CHECK_BUCKET=true`) does NOT fix it; the *write itself* is unauthorized. `rclone lsf` (read) still succeeds, masking it. Diagnose capabilities definitively via B2 native API: `curl -s -u "$KEY_ID:$KEY" https://api.backblazeb2.com/b2api/v3/b2_authorize_account` → capabilities live at `apiInfo.storageApi.capabilities` (v3 nesting; NOT top-level `allowed`).
- rclone native-env config (CWE-214-safe, no secret on argv): `RCLONE_CONFIG_PIPELINE_TYPE=b2 RCLONE_CONFIG_PIPELINE_ACCOUNT=$PIPELINE_B2_KEY_ID RCLONE_CONFIG_PIPELINE_KEY=$PIPELINE_B2_KEY`.

- **The GH read-only secret was never rotated after the 2026-07-08 split — the CONSUMER HAD NEVER WORKED (deploy#549). RESOLVED: owner rotated both secrets 2026-07-09 ~15:37Z.**
- **`deploy-data-load.yml` misreports that 401 as "no objects found ... is parquet_ref correct and published?"** — `verify_present()`/`glob_present()` do `rclone lsf "$dir/" 2>/dev/null || true`, collapsing auth/network/missing-binary failures into the empty-listing branch, which then asserts a *specific wrong cause* and sends you to the producer side. Same misdiagnosis class as the write-path 401 above. **Timing discriminates them:** valid-auth empty prefix returns in **~0.5s** (rc=0, empty); auth failure takes **~5s** (rclone retries `authorize_account`). Check elapsed time in the run log before believing "not published". **FIXED by deploy#552/PR#554 (merged 2026-07-09, `2ca7d10c`)**: `lsf_or_die` separates rc≠0 from rc=0-empty and exits on the former; remote script now under `set -euo pipefail`.
- **rclone reads EVERY option from an `RCLONE_<OPTION>` env var — an ambient one is a credential-leak vector in a PUBLIC repo's Actions log.** `RCLONE_LOG_LEVEL=DEBUG` / `RCLONE_VERBOSE=2` → rclone echoes `DEBUG : Setting key="<app key>" ... from environment variable` (plaintext; GH masking *does* scrub this). `RCLONE_DUMP=auth` → `Authorization: Basic <base64(keyId:appKey)>`, and **GH masking canNOT scrub it** — the scrub is an exact-substring match on the registered secret bytes and the base64 is different bytes. `noorinalabs-deploy` is PUBLIC, so its Actions logs are world-readable. An explicit `--log-level` beats a hostile `RCLONE_LOG_LEVEL`/`RCLONE_VERBOSE` but does **not** defeat `RCLONE_DUMP`. Guard (PR#554, L240, before the exports): scrub-loop `for _v in $(env | sed -n 's/^\(RCLONE_[A-Z0-9_]*\)=.*/\1/p'); do unset "${_v}"; done`, plus pin `rclone lsf --log-level NOTICE`. Ordering matters — after the exports it would unset the credential it protects.
- **No CI job shellchecks an `appleboy/ssh-action` `with: script:` body** — actionlint treats it as an opaque string (this is NOT the [[feedback_actionlint_needs_shellcheck]] silent-skip; CI does install shellcheck), and the `shellcheck (infra & scripts)` job globs only `*.sh`. The whole remote script of `deploy-data-load.yml` has always been unlinted — that gap is how deploy#552's missing `set -e` and a dead `# shellcheck disable=SC2254` directive (sat above an assignment, not the `case`) both shipped green. Tracked: **deploy#555** (proposed fix: extract bodies via `yaml.safe_load` and lint as `sh`, not `bash`).
- **B2 Class-B download cap (~1 GB/day free) is SMALLER than one full load (~1.11 GB) — a clean run exceeds it by itself (deploy#556).** `curated/` 243.778 MiB + `staging/` 818.996 MiB = ~1.11 GB decimal. Symptom: `403 download_cap_exceeded — download bandwidth or transaction (Class B) cap exceeded`. The presence check still PASSES (`rclone lsf` is Class C, not capped) — only the `rclone copy` fails, so this is NOT a publish/parquet_ref problem. Amplifier: the remote script `rm -rf`s `${LOAD_DATA_DIR}` every run, so **every retry re-downloads the full 1.11 GB** — today's three-defect debug sequence burned a day's egress per attempt. A fresh daily allowance buys roughly ONE attempt (B2 lets in-flight requests overshoot). **Only the owner can raise the cap (B2 console → Caps & Alerts); the orchestrator cannot.** Caching `${LOAD_DATA_DIR}` would fix retries but interacts with da#350 — a persisted Parquet dir + persisted `.last_loaded_manifest.json` is exactly when the `--incremental` skip-list hazard goes live (today the `:ro` mount keeps the manifest from persisting).
- **Probing a B2 object with a FULL object path is vacuous — `rclone copyto`/`cat`/`lsjson` resolve it as a DIRECTORY**, print `INFO: There was nothing to transfer`, and exit **rc=0 with zero bytes**. A nonexistent object returns the SAME rc=0, so such a probe cannot fail and "proves" whatever you hoped. Probe the way the workflow does: `rclone copy --include '<file>' '<dir>/' <dest>/` (rc=7 + the real 403 on a capped account). Always run the **nonexistent-object negative control** first; if it also returns rc=0 the harness is blind. (Also: `rclone … 2>&1 | head` returns *head's* rc — see [[feedback_push_pipe_masks_rejection]].) Instance of [[feedback_passing_repro_masks_bug]].
- **The Class-B cap is ACCOUNT-level, not key- or workflow-level.** Verified 2026-07-09: a 4,446-byte download 403s identically from the VPS with the read-only GH-secret key AND from the workstation with the write-capable local key. Size is irrelevant once the account is capped. `rclone lsf` keeps working throughout (Class C is a separate, uncapped counter) — so a passing presence check is NOT evidence the cap is clear. The 403 names TWO distinct caps (Daily Download **Bandwidth** and Daily Class B **Transactions**); they are separate fields on Caps & Alerts and raising one leaves the other enforcing. Exceeding the free tier also needs a payment method on file — the cap field accepts a larger number without granting egress if billing is off.
- **Repo-level Actions var `VPS_HOST` is the decommissioned/recycled `87.99.134.161`** (deploy#550); the correct stg host `87.99.137.225` is only at `staging`-**environment** scope. Env scope wins, so workflows declaring `environment:` are safe — but a `gh variable list --repo` read, or any SSH job lacking `environment:`, silently targets a recycled public IP.
- **CORRECTED 2026-07-09: `noorinalabs-prod` resolves correctly to `178.156.214.225`** (prod, rebuilt 2026-05-01). An earlier note here claimed the shared `Host noorinalabs-stg noorinalabs-prod` block made prod resolve to the staging box — that is **false** for the current `~/.ssh/config`, which has the shared block for `User`/`IdentityFile` plus **separate per-host `Host` blocks each with its own `HostName`**. Verify with `ssh -G noorinalabs-prod | rg '^hostname'` — never infer host identity from a config-file skim, and `hostname` on the box confirms it. A wrong belief here points destructive commands at the wrong machine.
